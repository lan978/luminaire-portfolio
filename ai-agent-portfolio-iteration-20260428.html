Multi-Agent Customer Service Portfolio Case

Multi-Agent 智能客服
迭代作品集

这份作品集主要展示我在本次迭代中完成的三件事：把原有 FAQ / RAG / Workflow 客服链路升级成由 Intent、Risk、Planning、Reply 协同决策的 Multi-Agent 处理链，补上 Trace、Judge 与 Bad Case 驱动的可观测修复机制，并通过单轮、多轮、投诉升级等真实测试用例逐条验证系统效果。

Multi-Agent Design

多智能体协同设计

Agent 01

IntentUnderstanding Agent

负责识别用户当前想做什么，并结合商品焦点、订单号、当前任务状态判断这是不是追问、换话题还是进入新的售后阶段。

能力边界：只负责理解，不直接决定调用哪个工具。
处理任务：商品咨询、物流查询、退款意图、模糊售后、投诉表达识别。
Agent 02

RiskCompliance Agent

负责识别用户情绪、投诉风险、补偿争议和是否应该优先人工接管，让风险判断不再混在普通回复逻辑里。

能力边界：只负责判断风险，不直接执行工单创建或业务动作。
处理任务：物流抱怨、服务不满、投诉升级、赔偿争议、人工兜底建议。
Agent 03

Planning Agent

负责决定下一步应该怎么处理：继续追问、查订单、调用 RAG、判断售后条件，还是直接进入人工接管。

能力边界：负责决策路径，不直接生成最终客服话术。
处理任务：调用 order_tool、rag_tool、after_sale_tool、create_handoff_ticket 等稳定工具。
Agent 04

Reply Agent

负责把前面几层的判断结果转成用户真正看到的话术，保证回复内容和用户问题焦点一致，语气和风险等级匹配。

能力边界：不重新做业务判断，而是基于已有结论生成合适回复。
处理任务：商品问答聚焦、物流安抚、售后说明、人工接管提示。
Support Layer 01

Trace 与评测模块

这部分不参与前台决策，而是放在链路后方记录每一轮对话的意图、风险、规划、工具调用和最终动作，并把失败样本沉淀成可复盘的 Bad Case。

能力边界：不直接处理用户问题，专注于记录、归因、评测和回归验证。
处理任务：Trace 记录、Judge 评测、Bad Case 收集、OptimizationAdvisor 建议。
Support Layer 02

稳定工具层

下面这些是 PlanningAgent 在白名单内可以调用、并由稳定工具层执行的确定性工具。

商品知识：FAQ 工具、商品 RAG 检索工具
订单履约：订单查询工具、物流查询工具
售后处理：售后判断工具、售后建议工具、退款 / 退货 / 换货处理工具
人工协同：转人工工单创建工具、人工工单复用工具
Execution Loop

一轮用户请求，如何进入 Multi-Agent + Harness 的执行闭环

这次迭代不是“多加几个 Agent”，而是把原来“命中分支后执行”的固定 Workflow， 升级成“先理解情况，再判断风险，再决定怎么处理”的智能执行链路。 面向电商客服场景，真正关键的不是 AI 会不会答，而是它能不能在复杂诉求下既保持灵活，又不越过合规红线。

Harness Full Chain Control
Harness 不是另一个智能体，而是包裹整条链路的确定性管控外壳
高风险命中即中断并转人工
用户请求 -> Risk Agent + 状态机 -> Intent Agent -> Planning Agent -> 稳定工具层 -> Reply Agent -> Reply Guard -> Trace / Harness 审计 -> 系统输出 / 转人工
Control Layer

Harness 管控层：不是再加一个总控 Agent，而是把 AI 的灵活性锁进合规边界里

电商客服场景里，AI 的灵活性与合规确定性天然冲突。没有 Harness，系统要么像老式 Workflow 一样死板， 要么像“自由发挥”的智能体一样容易越权承诺、误判状态、放大客诉。 我把 Harness 设计成全链路之外的确定性管控内核，用代码规则而不是额外的智能体去守住红线，同时保留 Multi-Agent 对复杂诉求的理解和规划能力。

Business Conflict

为什么必须做 Harness

传统 FAQ / Workflow 路由太早，用户一旦表达模糊、跨状态、带情绪，系统就容易走错分支。 但如果完全放开给智能体自由决策，又会在退款、赔付、投诉升级这类高风险场景里踩线。

Product Answer

Harness 解决的不是技术炫技，而是业务矛盾

我没有推翻原有 FAQ、RAG、订单查询、售后判断这些稳定工具，而是只升级调度权。 系统从“命中分支后执行”变成“先理解情况，再判断风险，再决定怎么处理”。

Core Value

核心价值

这个方案的核心价值，不是“多做了几个 Agent”，而是在保留原有稳定工具能力的前提下， 把客服系统从固定路由升级成可理解上下文、可判断风险、可规划动作的智能决策系统， 同时用 Harness 守住合规底线，让它真正具备上线、审计和持续迭代的条件。

4 Layers
Layer 01 对应 ST18 高风险投诉 100% 拦截

全局状态机：固定执行顺序，不允许越级跳步

所有请求必须先过风险初筛，再进入意图识别、任务规划、工具执行和回复生成。 一旦命中 12315 投诉、赔付争议、高风险客诉，状态机立即中断链路并转人工。 它解决的是“AI 还没看清风险就已经开始执行”的问题。

Layer 02 对应 ST12 / ST19 禁止越权 / 禁止状态乱跳

分布式权责锁：把软提示词边界变成硬代码约束

Intent Agent 只能输出预设枚举意图，Risk Agent 只负责风险判断，Planning Agent 只决定路径与工具， Reply Agent 不能直接越权承诺退款、赔付或平台责任。它解决的是“谁都能做一点，最后没人能解释为什么这么做”的黑盒问题。

Layer 03 对应 ST17 只拦截，不调度

轻量 Reply Guard：只做最终质检，不参与流程调度

Reply Guard 没有调度权，只负责最终兜底：空回复自动改写、违规承诺直接拦截、高风险话术自动补齐。 它解决的是“前面流程没问题，但最后一句话把系统带进合规事故”的尾部风险。

Layer 04 对应 MT04 / MT09 / MT10 / MT11 / MT12 Bad Case 秒级定位

统一 Trace / Harness 审计：让每次决策都可追溯、可复盘、可回归

每轮请求共用一条 Trace ID，统一记录风险判断、意图识别、规划结果、工具调用、状态迁移、锁拦截和 Reply Guard 质检结论。 所以下面的测试截图不只是证明“答对了”，而是能精准定位“错在哪一层”，形成测试 - 定位 - 优化 - 复测的闭环。

One Sentence

一句话总结这套 Harness：它不是“再造一个会思考的总控大脑”，而是给整套 Multi-Agent 系统加上 固定路权、权限闸门、最终质检和全程记录，让 AI 能解决复杂业务问题，但绝不以牺牲合规为代价。

Execution Loop

一轮用户请求如何进入多智能体闭环

从用户问题进入系统开始，请求会先经过风险判断，再进入意图识别、任务规划、工具执行和回复生成。 其中 Reply Agent 负责生成最终客服话术，Reply Guard 负责做最后质检；如果命中高风险，状态机会直接打断链路并转人工， 如果正常通过，则由系统执行“返回用户”这个最终输出动作。

用户问题 → RiskCompliance Agent → IntentUnderstanding Agent → Planning Agent → 稳定工具层 → Reply Agent（生成回复） → Reply Guard（最终质检） → Trace / Harness 审计 → 系统输出：返回用户 / 转人工
Control Layer

Harness 管控层：让多智能体系统可控、可审计、可回归

Full Flow
Step 01

风险分析智能体 + 状态机

先做高风险初筛；命中 12315 投诉、辱骂、赔偿争议时，状态机直接中断并转人工。

Step 02

意图识别智能体

结合商品焦点、订单号、当前任务状态识别用户意图；输出必须落在预设枚举范围内。

Step 03

计划制定智能体

决定下一步是继续追问、查订单、调 RAG、走售后判断还是直接转人工。

Step 04

分布式权责锁

把软提示词边界变成硬代码约束：意图必须合法，工具必须在白名单内，不能越权调用。

Step 05

稳定工具层

执行 FAQ、商品 RAG、订单查询、物流查询、售后判断、工单创建等具体动作。

Step 06

Reply Agent：生成回复

把前面各层的判断结果组织成最终客服话术，保证内容、语气和风险等级匹配。

Step 07

Reply Guard：最终质检

只做最终质检：空回复自动改写，违规承诺直接拦截，高风险场景补全标准转人工话术。

Step 08

系统输出 + Trace / Harness 审计

系统执行“返回用户 / 转人工”动作，同时统一记录意图、风险、规划、工具、状态迁移、锁拦截和异常兜底。

Layer 01

全局状态机：固定执行顺序，不允许越级跳步

对应链路位置：用户输入 → 风险初筛 → 意图识别 → 任务规划 → 工具执行 → 回复生成。 所有用户输入都必须先过风险初筛，再进入意图识别、任务规划、工具执行和回复生成。 一旦命中 12315 投诉、赔偿争议或高风险标签，状态机直接强制转人工，不允许进入后续智能体环节。

Layer 02

分布式权责锁：把软提示词边界变成硬代码约束

对应链路位置：意图识别、任务规划、回复生成三层。 意图输出必须是预设枚举值；风险标签拥有系统最高优先级；PlanningAgent 只能调用白名单内工具； Reply 层禁止输出“全额赔偿、平台负责、保证退款”等违规承诺，触发后直接拦截。

Layer 03

轻量 Reply Guard：只做最终质检，不参与流程调度

对应链路位置：回复生成之后、返回用户之前。 这层只负责最终回复兜底：空回复自动改写，高风险转人工话术缺失时自动补全，出现违规承诺时直接转人工。 它只有拦截权，没有调度权，不会反过来影响上游智能体的执行顺序。

Layer 04

统一 Trace / Harness 审计：决策与管控共用同一条 Trace ID

对应链路位置：覆盖整条执行路径，从风险初筛一直记录到最终输出。 Trace 记录意图、风险、规划、工具和最终回复；Harness 额外记录状态迁移、锁拦截和 Reply Guard 质检结果。 所以后面的测试用例不只看“答得对不对”，还可以直接定位失败发生在哪一层。

Before / After

前后版本对比

Before

V1 · FAQ / RAG / Workflow

链路与识别过程
用户问题进入系统后，会先做 rewrite / intent 识别，再由 router 按预设规则决定走 FAQ、RAG、订单流程、售后流程或人工转接。也就是说，链路大多是提前设计好的，真正交给智能体临场决策的空间比较少。
保留下来的优点
标准化问题稳定，FAQ / RAG / Workflow 边界清楚，订单、物流、售后这些业务工具执行路径明确。
核心短板
路由被决定得太早。遇到模糊售后、多轮追问、情绪升级或订单上下文承接时，系统更像“命中分支后执行”，而不是“先理解情况、再判断风险、再决定怎么处理”。
After

V2 · Multi-Agent 协同决策

链路升级
相对上一版“先命中路由、再进入分支执行”，这一版把关键判断前置成一条多智能体链路：先由 RiskCompliance Agent 判断风险边界，再由 IntentUnderstanding Agent 理解用户诉求和上下文，最后交给 Planning Agent 决定下一步该追问、查订单、调 RAG、走售后还是转人工。
保留与重构
FAQ、RAG、订单 / 售后 Workflow 没有被推翻，而是从“直接决定回复的链路”重构成“被 Planning Agent 调度的稳定工具包”。也就是说，上一版积累下来的工具能力被保留下来，但调度权从固定路由升级成了智能规划。
这次真正新增的能力
新增的不只是几个 Agent 名字，而是整套决策能力：上下文复用、投诉升级策略、人工工单复用、Harness 状态机与权责锁、Reply Guard、统一 Trace / Harness 审计，以及 Bad Case 回归验证闭环。系统开始具备“先理解情况，再决定怎么处理”的能力。

Methodology

这组数据是怎么测出来的

1. 样本池直接解析当前作品集测试矩阵，覆盖 32 组单轮用例 + 12 组多轮用例，总计 44 组会话 / 67 轮用户输入，确保“页面展示的用例”和“最后展示的指标”完全同源。

2. 每一组会话开始前，都会通过 DataResetService 重置演示订单、物流、售后记录和人工工单， 避免上一组测试污染下一组结果。

3. 每组会话使用一个新的 CustomerServiceAgent 实例；只有在同一组多轮对话里，才复用同一个 Agent， 这样才能真实验证订单焦点、商品焦点和 pending task 是否能被持续绑定。

4. 全量套件重复执行 3 次。功能指标按首轮完整结果统计，TTFT 取三轮汇总后的均值 / 分位值， 再额外检查每组会话在 3 次运行中的意图、路由、澄清和转人工签名是否一致。

5. 当前评测脚本位于 tests/evaluation/run_portfolio_runtime_metrics.py， 结果快照输出到 tests/eval_results/portfolio_runtime_metrics_latest.json 和 .md，方便后续复测和追溯。

Metric Definition

指标口径

TTFT： 当前非流式架构下，从进入 handle_message() 到 UI 可接收首个回复对象之间的耗时， 它衡量的是本地编排链路与工具执行延迟，不是云端逐 token 输出速度。

人工干预率： 只要任一轮对话触发人工路由、生成工单或明确标记需要 handoff，就计入人工介入。

意图澄清： 当路由进入 agentic_clarification，或 Agent 决策动作是 ask_clarification 时，记为一次澄清。

Environment Note

当前结果适用于什么环境

本轮评测运行在 assist mode，且 Agentic Decision LLM = off 的本地演示环境里。

这意味着这里的 TTFT 和人工干预率，主要用来证明 编排稳定性、Harness 管控有效性和测试可复现性； 如果后续接入真实外部模型，延迟数值会变化，但“是否稳定走对流程、是否该拦截就拦截、是否能把澄清收敛成有效处理”这套验证方法仍然成立。

在当前环境下，3 次重复运行的会话签名一致率为 100%，说明这套测试可以稳定复现同一批结论。
