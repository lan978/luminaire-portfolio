Problem Context

复杂售后场景下的服务瓶颈

传统问答系统只能覆盖 FAQ，难以进入订单、物流和售后等真实业务动作； 一旦进入复杂争议场景，AI 与人工之间就会出现明显断点。

客服工作量痛点分布 (示意)

1

标准问题与复杂问题并存

物流、FAQ 等高频问题适合自动化处理，但售后争议、退款判断、异常状态识别需要更强的业务链路能力。

2

知识更新滞后直接影响应答质量

商品知识、政策规则、FAQ 一旦维护不及时，就会导致 RAG 命中不稳、话术不准，进而扩大 bad case 数量。

3

AI 与人工协同链路容易断裂

转人工后若无法继承前序对话、订单与风险判断，客服就需要重新理解上下文，用户也会失去连续服务体验。

Scenario Breakdown

场景拆解

电商售后不是单一问答场景，而是由售前、售中、售后与高风险场景共同构成。 先拆清问题类型，后续的分层路由设计才有依据。

Scene 01

售前场景

以商品咨询和推荐为主，强调属性理解、知识命中与回答准确性。

典型问题：尺码、版型、材质、洗护、穿着建议
核心能力：FAQ + 商品知识 RAG
Scene 02

售中场景

订单和物流状态查询频次高，适合标准化流程处理，但需要接入真实业务状态。

典型问题：发货时间、物流进度、地址修改、支付状态
核心能力：Workflow 查询 + 状态管理
Scene 03

售后场景

退换货、退款与换货判断依赖订单状态、政策规则与上下文，业务复杂度显著提高。

典型问题：退货退款、换货、签收异常、售后条件判断
核心能力：规则判断 + Workflow + 人工接管
Scene 04

高风险场景

一旦涉及争议、投诉、边界不清或服务失败，就必须将“自动处理”切换为“风险控制优先”。

典型问题：仅退款争议、投诉升级、复杂情绪、边界不清售后
核心能力：风险识别 + 工单流转 + 人工兜底

Routing Strategy

场景与处理链路的对应关系

FAQ 规则层
优先承接标准问法和固定规则问题，保证高频问题低成本处理。
RAG 检索层
处理商品属性、政策规则、长文本知识问答，降低模型幻觉。
Workflow 业务层
接入订单、物流、库存、售后等真实业务状态，推动系统执行而不只是回答。
人工兜底层
在高风险、复杂争议和边界不清场景中接管服务，保障用户体验与结果可控。

Goals & Principles

产品目标与设计原则

目标不是简单接入大模型，而是围绕业务效率、服务体验和风险控制， 搭建一套既能自动承接、又能稳定协同人工的售后服务体系。

Product Goals

希望解决什么问题

提升标准问题自动化效率
让高频 FAQ、商品咨询、订单和物流查询优先被系统自动承接，释放人工产能。
增强复杂售后判断能力
让退款、换货、争议和高风险场景不再停留在模糊问答，而是进入真实的决策链路。
打通用户端与客服工作流
减少转人工后的信息丢失，让客服可以直接继承上下文继续处理。
建立可评测、可优化的演进机制
通过评测与 bad case 回流，让系统具备持续优化能力，而不是一次性交付。
Principle 01

分层路由，不做纯大模型直答

优先用 FAQ、RAG、Workflow 与人工兜底分层承接，不把复杂业务直接交给单一大模型判断。

Principle 02

先准确承接，再追求表达体验

在业务场景里，回答“好听”不如判断“正确”。所有界面和流程都围绕准确承接服务诉求展开。

Principle 03

高风险场景优先考虑人工兜底

当系统识别到复杂争议、边界不清或情绪风险时，应优先控制风险，而不是强行自动化完成。

Principle 04

让数据和 bad case 驱动产品迭代

通过转人工率、场景分布和异常案例来定义问题优先级，让优化动作有依据、有验证、有结果。

Core Mechanism

四层处理机制与多角色协同生态

这不是单纯的对话页，而是把用户服务入口、客服工作台、知识库运营后台和评测数据看板串成一个可运营、可评测、可迭代的服务闭环。

Layer 1

FAQ 规则层

优先处理高频固定问题，保证基础场景的响应速度与准确度。

Layer 2

RAG 检索层

结合商品静态知识与长文本政策，提升长尾问法和商品问答的稳定性。

Layer 3

Workflow 业务层

驱动订单、物流、售后、库存等真实动作，让 AI 进入业务流程而非停留在问答。

Layer 4

人工兜底层

高风险、复杂争议与边界不清场景自动转接人工，保障服务结果可控。

用户 (Client)

在统一入口发起商品咨询、物流查询与售后请求。

客服专员 (Specialist)

承接 AI 无法稳定处理的问题，继承上下文并继续完成服务。

知识运营 (Strategist)

维护知识资产，排查异常 chunk，修复线上 bad case 根因。

产品策略 (Director)

通过转人工率、场景分布与 bad case 记录推动版本优化。

Agent Engineering

Agent 工程化能力：把方案设计成可控链路

以换货 Bad Case 为例，展示我如何基于 Trace 链路定位问题，再从意图字段、MCP 工具、业务规则和风险控制四个层面完成迭代闭环。

1. 问题定位 基于 Trace 链路发现换货意图标签、关键字段和自动换货工具配置缺失，同时换货逻辑未区分订单状态、换货条件和异常兜底；系统只能追问订单号，若直接自动执行会带来库存、资金和客诉风险。
2. 迭代行为 补充“换货、用户同意换货、换货尺码/颜色”等意图字段，配置 MCP 自动换货工具的参数、调用条件和输出格式，并按真实售后规则重构换货状态分支。
3. 风险控制 工具调用前必须校验订单号、目标尺码/颜色、用户同意、可换货状态和库存；不满足条件先追问，修改需求、高风险场景或二次确认失败则转人工。
4. 全局思考 从逻辑严谨性、状态一致性、多智能体链路、成本、推理时间和稳定性评估迭代方案。
5. 测试验证 设计换货测试样本并进行人工测试，验证换货逻辑能完整跑通，且追问、工具调用、二次确认和转人工分支无异常。

迭代前：系统只要求用户提供订单号，未能基于“尺码不合适”识别换货需求，也没有进入售后规则判断链路。

Dialogue 01

焦点商品记忆 + 多轮连续追问 + 商品知识 RAG 问答

这一组对话重点证明：当用户已经明确商品后，系统能够持续记住当前焦点商品，并在材质、洗护、适穿场景等连续追问下维持同一商品语境，不会被相似商品错误带偏。

验证链路商品识别 → 焦点商品记忆 → query rewrite → 商品知识 RAG 回答。
用户动作先问“重磅230g纯棉宽松短袖T恤适合什么季节穿”，再追问“100%纯棉的吗”“可以机洗吗”。
想证明的能力商品记忆、多轮追问承接、属性型问题的稳定回答。

Dialogue 02

新商品优先识别 + 焦点商品切换 + 跨商品多轮问答

这一组对话用来证明系统不是只会围绕一个商品重复回答，而是能够在用户明确提出新商品时优先切换焦点，并让后续“这款”“那这件”之类的追问自动承接新的商品对象。

验证链路新商品实体识别 → 焦点切换 → 库存 / 属性问答 → 跨商品连续承接。
用户动作先问 T 恤材质，再切到“抗皱高腰西装裤有哪些尺码”，最后追问“那这款适合通勤穿吗”。
想证明的能力多商品上下文切换、商品优先识别、跨商品多轮问答的稳定性。

Dialogue 03

售后意图识别 + 订单号追问 + 事务型 Workflow 连续处理

这一组对话重点展示系统如何把模糊售后咨询转成可执行流程：先识别退款意图，再追问订单号，最后进入具体的事务处理链路，并承接“多久到账”这类后续售后问题。

验证链路售后意图识别 → 订单号补全 → 事务型 workflow → 后续售后解释。

想证明的能力事务型流程设计、状态承接、订单号追问恢复和售后规则解释。

Dialogue 04

高风险场景识别 + 人工兜底 + 风险控制边界

这一组对话用于证明系统在投诉、赔偿、情绪升级等高风险场景中不会盲目自动化，而是优先进入人工兜底机制，并同步工单号与后续承接信息，确保服务结果可控。

Version History

版本迭代记录

这个项目的价值不在于一次性把功能堆满，而在于围绕真实问题逐步补齐能力边界。 我将迭代拆成四个阶段，每一步都对应一个更明确的业务目标。

Version 1

V1.0

先搭建 FAQ + RAG 的基础问答能力

先验证商品咨询、基础 FAQ 与知识检索链路是否成立，让系统能够稳定回答高频标准问题。

Why This Version

优先证明智能问答能力可用，建立最小可运行版本。

What Changed

完成 FAQ 规则拦截、商品知识 RAG 和基础用户对话入口。

Version 2

V2.0

把 AI 问答推进到业务流程里

不再停留在“能回答”，而是开始接入订单、物流和售后流程，让系统能做业务判断和状态承接。

Why This Version

解决“传统 AI 客服只能答，不能办”的核心问题。

What Changed

引入 Workflow 处理订单与物流场景，并补充售后判断与转人工链路。

Version 3

V3.0

补齐人机协同与知识运营后台

把客服工作台和知识库管理独立出来，让系统具备人工介入、知识维护和异常修复能力。

Why This Version

解决 AI 与人工链路断裂，以及知识无法快速修复的问题。

What Changed

完成 handoff_tickets、客服工作台、文档上传、chunk 可视化与知识节点管理。

Version 4

V4.0

建立评测、Bad Case 与数据看板闭环

在系统可运行后，进一步补上评测和复盘机制，让优化不依赖主观感受，而是回到数据和坏例上。

Why This Version

让系统具备持续迭代能力，而不是停留在一次性交付。

What Changed

增加离线评测、开放问法补充评测、bad case 回流与数据看板，支撑版本优化。
